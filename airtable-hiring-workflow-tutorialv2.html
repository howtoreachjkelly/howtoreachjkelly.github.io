Building an enterprise hiring workflow in Airtable

A table-by-table, click-by-click guide to building a real requisition → candidate → interview → offer → approval pipeline — the kind large companies run recruiting on, built without a single line of code.

Before you start

One mental model to hold onto for the entire build.

Coming from spreadsheets, the instinct is one giant tab with a column for everything. Airtable's actual advantage only shows up once you split that into separate tables for separate things — a candidate, a job requisition, an interview — and connect them with Link to another record fields instead of retyping text.

Everything in this guide — lookups, rollups, automations — is built on top of that one idea. Get the linked-record structure right first; everything else is decoration on top of it.

Setup Create a new base from scratch (not a template) at airtable.com → Add a base → Start from scratch. Name it Hiring Workflow. You'll add 8 tables to it over the next 8 steps.
Pasting into Link fields can silently fail When you get to populating tables with data, pasting plain text into a Link to another record column sometimes does nothing at all — no error, no dialog, just no change — with no consistent trigger identified. If it happens: test whether your clipboard actually has anything in it first (paste into a plain text field to check), try right-click → Paste instead of Ctrl/Cmd+V, and confirm the field you're pasting into is actually a Link field and not a read-only Lookup that looks similar. If it still won't take the paste, the reliable fallback is linking records one at a time by hand (click the cell → expand/search icon → pick the record), or using the CSV Import extension (Tools → Extensions → add "CSV import"), which is built to write into Link fields directly during column mapping.

Departments & People

The foundation tables — everything else in the base links back to these, so get them right first.

Table: Departments

  1. Click + Add or import at the bottom of the table bar → Create blank table. Rename it Departments.
  2. Rename the default Name field (it's your Primary field — every table needs exactly one, it's what shows up when this table is referenced elsewhere).
  3. Add field VP Owner — type Link to another record → target table People (create People first if it doesn't exist yet, or leave this field for later and come back to it).
  4. Add field Budget Headcount — type Number, integer format.

You'll add an Open Reqs rollup field here later, once the Requisitions table exists — rollups can only reference tables that already exist.

Table: People

Every recruiter, hiring manager, interviewer, and approver in the org goes here — this is the table that makes the approval chain in Step 5 possible.

Leave Applications, Approvals, and Candidate Count for later — Airtable auto-creates the reverse link once you build the Applications and Approvals tables and link back to Requisitions from there.

Why status is a single select, not text A Single Select field is what an automation can watch for changes on ("when Status becomes Pending Approval, do X"). A plain text field can't trigger anything — this distinction matters everywhere in this build.
Why Recruiter lives here, not on Applications One recruiter owns a requisition end to end, across every candidate in it — not one recruiter per candidate. Put Recruiter here, on Requisitions, and pull it into Applications and Interviews later as a Lookup rather than re-entering it per record. It gets assigned by whoever manages recruiter capacity, typically right when a req moves from Approved to Open.
Autonumber not filling in Renaming the default first field to Req ID doesn't make it an Autonumber — check Edit field and confirm the type actually says Autonumber, not Single line text. Even when it's correctly set, a batch of records added all at once (bulk paste, or several created in the same automation run) can leave some rows unnumbered. Fix: Edit field → switch the type away from Autonumber to Number or Text → save → switch it back to Autonumber. This recomputes every record's number from scratch based on creation order — fine here, but worth knowing it renumbers everything, not just the blank ones.

Table: Applications — the junction table

A candidate can apply to multiple reqs. A req gets multiple candidates. That's a many-to-many relationship, and Airtable has no direct way to link two tables many-to-many — you always need a third table sitting in between, with a single link to each side. That's what Applications is.

FieldTypeNotes
Application IDFormulaPrimary field — see below
CandidateLink to recordLinks to Candidates, single record only
RequisitionLink to recordLinks to Requisitions, single record only
StageSingle selectApplied / Phone Screen / Onsite / Offer / Hired / Rejected
RecruiterLookupThrough the Requisition link, sourcing Requisitions → Recruiter
{Candidate} & " → " & {Requisition}

Recruiter is a Lookup here, not its own Link field — it's set once on Requisitions and flows down automatically. Add it after you've built Requisitions' Recruiter field in Step 2.

The pattern to remember Any time you hit "this could link to more than one of that, and that could link to more than one of this" — stop, and build a junction table instead of trying to force a direct link. You'll see it again with Interviews and Approvals.

Back on the Applications table — add two rollups now

With Interviews built, go back to Applications and add:

FieldTypeConfig
Avg Interview ScoreRollupThrough the Interviews link — see formula below, not bare AVERAGE
IF(COUNT(values) = 0, "", AVERAGE(values))

Bare AVERAGE(values) shows NaN for any candidate with zero linked Interviews yet — averaging nothing is undefined. The COUNT check shows a clean blank cell instead until there's actually something to average.

A Lookup pulls one linked record's field over as-is. A Rollup aggregates across multiple linked records with a function like SUM, AVERAGE, or COUNT. Use Lookup for "what's this candidate's name," Rollup for "what's the average score across all their interviews."

05

The approval chain

⬤ hardest step in this build

A checkbox that says "manager approved" is a single gate, not a chain. A real chain means multiple approvers acting in sequence, where step 2 can't act until step 1 clears. Do everything else in this guide first — come back here once the rest of the base is stable.

Table: Approvals — a generic, reusable approval engine

One table handles req sign-off and offer sign-off — you don't need two separate systems.

FieldTypeNotes
Approval IDFormulaPrimary field
TypeSingle selectReq Approval / Offer Approval
Related ReqLink to recordBlank for offer approvals
Related OfferLink to recordBlank for req approvals
ApproverLink to recordLinks to People
Approval OrderNumber1, 2, 3 — this is what makes it a sequence
StatusSingle selectPending / Approved / Rejected
CommentsLong text

Wiring the chain — five steps

  1. Requisition's Status changes to Pending Approval. An automation (built in Step 6) creates several linked Approval records at once — e.g. Order 1 = Dept VP, Order 2 = Finance, Order 3 = CHRO — branching on the req's Priority or Salary Band.
  2. Every Approval record starts as Pending.
  3. Build a view filtered to Approver = me AND Status = Pending — but add one more condition: a formula field that checks whether every lower Approval Order on the same req is already Approved. That formula is the actual gate — it's what keeps approver #2 from seeing the request before approver #1 has acted.
  4. When the last approver in the chain sets Status to Approved, an automation flips the parent Requisition to Approved.
  5. If any approver Rejects, an automation flips the Requisition back to Draft and notifies the Hiring Manager.
Where people get stuck The gate in step 3 is a formula field, not a filter you can build with dropdowns alone. If you're new to Airtable formulas, this is worth a dedicated session rather than trying to knock it out alongside everything else.
06

Automations

Automations tab, top of the base. Build these in order — later ones reuse patterns from earlier ones. Test every step individually before toggling an automation on; the on/off toggle sits in the upper-left of the automation panel and often won't do anything until each step has passed a test.

Two trigger types, don't mix them up When a record is created — only for #1, a brand-new record showing up. When a record matches conditions — for everything else, since it fires the moment a field reaches a specific value and lets you set that condition inline. When a record is updated looks similar but has no inline condition support, only a list of fields to watch — easy to reach for by mistake and then wonder where the condition builder went.

1. New Application created → set Stage, notify Recruiter

  1. Trigger: When a record is created — table Applications.
  2. Action — Update record: table Applications. Record ID → dynamic value → trigger step's Airtable record ID (not any other ID-looking field). Set Stage → Applied.
  3. Action — Send an email/Slack message: recipient → trigger record's Recruiter (now a Lookup pulled from Requisitions). Subject referencing {Candidate} and {Requisition} as dynamic tokens.

2. Req Status → Open with no Recruiter → notify for assignment

  1. Trigger: When a record matches conditions — table Requisitions. Conditions: Status is Open and Recruiter is empty.
  2. Action — Send an email/Slack message: recipient → trigger record's Hiring Manager (or a fixed recruiting-ops address). Subject: Recruiter needed: {Job Title}.

3. Application Stage → Onsite → create Interview shells

  1. Trigger: When a record matches conditions — table Applications. Condition: Stage is Onsite.
  2. Action — Create record (Technical): table Interviews. Application → dynamic value → trigger record. Interview Type → Technical. Status → Scheduled.
  3. Action — Create record (Panel): same table, same trigger-record link — set the Application field again on this action separately, it does not carry over from the first Create Record action. Interview Type → Panel.
Two gotchas that hit here specifically When multiple records get created in the same automation run, the Interviews table's Autonumber primary field sometimes only assigns a number to the first one — fix with the same "switch away from Autonumber and back" trick from Step 2. And each Create Record action needs its own Application field mapped — it's easy to fill it in on the first action and forget the second needs the same dynamic value added separately.

4. Req Status → Approved → set to Open, notify Recruiter

  1. Trigger: When a record matches conditions — table Requisitions. Condition: Status is Approved.
  2. Action — Update record: Record ID → trigger's Airtable record ID. Set Status → Open. Set Date Opened → dynamic value's "Now"/"Today" option.
  3. Action — Send an email/Slack message: recipient → trigger record's Recruiter (blank at this point on most reqs — that's fine, automation #2 is what catches the empty case).

5. Offer Status → Pending Approval → create Offer Approval chain

  1. Trigger: When a record matches conditions — table Offers. Condition: Status is Pending Approval.
  2. Action — Find records (rename "Find Finance VP"): table People. Conditions: Department is Finance and Role is VP — both fixed values, since every offer needs the same Finance sign-off regardless of department.
  3. Action — Create record (Order 1): table Approvals. Type → Offer Approval. Related Offer → trigger record. Approver → left blank, filled in by hand once the record exists. Approval Order → 1. Status → Pending.
  4. Action — Create record (Order 2): same table. Approver → dynamic value → "Find Finance VP" result → Airtable Record ID (not Name/ID/JSON — those are for scalar comparisons, this one needs the actual record reference to populate a Link field). Approval Order → 2.
Why Find Records instead of a fixed name Hardcoding a specific person (e.g. "Ben Turner") breaks the day that person changes roles. Finding by Department is Finance, Role is VP means the automation keeps working if the actual person in that seat changes — you're looking up a role, not a name.

6. Req Status → Pending Approval → create Req Approval chain

Simplified from the original design — one approver (the department VP) rather than a two-step Dept VP + Finance chain. Cut Finance out entirely for requisitions since it's a headcount decision, not money leaving the building yet; that distinction is why Offers (automation #5) still keeps its two-step chain while this one doesn't.

  1. Trigger: When a record matches conditions — table Requisitions. Condition: Status is Pending Approval.
  2. Action — Find records (rename "Find Dept VP"): table People. Conditions: Department is exactly → dynamic value → trigger record's Department → Name (drilling into a link field for a condition comparison exposes Name / ID / JSON String / Length — Name is the one that matches text-to-text here) and Approval Level is Exec Approver (fixed).
  3. Action — Create record: table Approvals. Type → Req Approval. Related Req → trigger record → Airtable Record ID (not Name — see error callout below). Approver → "Find Dept VP" result → Airtable Record ID. Approval Order → 1. Status → Pending.
  4. Action — Send an email/Slack message: recipient → "Find Dept VP" result. Subject: Req approval needed: {Job Title}.
Approval Level vs. Role People.Approval Level (None / Dept Approver / Exec Approver) was built specifically to mean "this person can approve things" — a better fit for this Find Records condition than Role, which really describes job function. Keep the Department condition alongside it, not instead of it — filtering on Approval Level alone returns every Exec Approver company-wide, not the one for this req's specific department.
Error: "could not find matching rows for string" Shows up on a Create Record action when a Link field (like Related Req or Approver) gets fed a plain-text value instead of an actual record reference — Airtable tries to text-match it against the target table and fails. Check every Link field on the action: each one should be set to a dynamic value drilled down to Airtable Record ID, never Name or any other sub-field.

One specific variant of this: the error names Related Offer even though this is a Req Approval action — that means Related Offer picked up a stray mapping (easy to happen if this action started as a copy of the Offer automation's Create Record step) while Related Req was never actually added to the field list at all. Fix: add Related Req as a field on this action (dynamic value → trigger step → Airtable Record ID), and remove the Related Offer mapping entirely — it shouldn't be set on this automation at all.

7. Req Approval cleared → flip Requisition to Approved

  1. Trigger: When a record matches conditions — table Approvals. Conditions: Type is Req Approval and Status is Approved.
  2. Action — Find records (rename "Find Unapproved Steps"): table Approvals. Conditions: Related Req is → dynamic value → trigger record's Related Req → Name, and Status is not Approved (fixed). This surfaces any other step tied to the same req that hasn't cleared yet.
  3. Action — Condition ("Only continue if..."): Find Unapproved Steps → Length is 0. Everything after only runs if nothing's left pending.
  4. Action — Update record: table Requisitions. Record ID → trigger record's Related Req → Airtable Record ID. Set Status → Approved.
  5. Action — Find records (rename "Find Req Details", optional — only needed for the notification): table Requisitions. Condition: Job Title is exactly → trigger record's Related Req → Name. Reason this exists: drilling into a plain Link field only exposes Name/ID/JSON/Length — reaching an arbitrary field like an email requires a real Find Records step, which exposes a "Field Values" option instead.
  6. Action — Send an email: recipient → "Find Req Details" → Field Values → Hiring Manager Email (a Lookup field on Requisitions, add it if it doesn't exist yet — Lookup through Hiring Manager, sourcing Email). Subject: Requisition fully approved: {Job Title}.

8. Offer Approval cleared → flip Offer to Approved

Same shape as #7, mirrored onto Offers.

  1. Trigger: When a record matches conditions — table Approvals. Conditions: Type is Offer Approval and Status is Approved.
  2. Action — Find records ("Find Unapproved Offer Steps"): table Approvals. Conditions: Related Offer is → trigger record's Related Offer → Name, and Status is not Approved.
  3. Action — Condition: Find Unapproved Offer Steps → Length is 0.
  4. Action — Update record: table Offers. Record ID → trigger record's Related Offer → Airtable Record ID. Set Status → Approved.
Test end to end once all 8 are on Push one candidate through the whole pipeline by hand: Application created → Stage to Onsite → confirm both Interview shells appear correctly linked → create an Offer → set it to Pending Approval → approve both Approval records in order → confirm the Offer flips to Approved. Do the same for a Requisition through its own approval chain. That's the full gate mechanism from Step 5 actually running.

08

Interfaces & permissions

The last mile — handing this to people who should never see the raw base.

Airtable's Interfaces layer builds a dashboard on top of your views — this is how you hand the base to an exec without teaching them what a grid view is. Build views first (Step 7), then build Interfaces from them; if you rebuild the underlying view later, the Interface needs rework, so don't build Interfaces until the views are stable.

Field-level and record-level permissions (an interviewer edits their own score but can't see salary bands) require Airtable's Enterprise plan admin panel — Team and free plans only permit locking at the table level. On lower plans, the workaround is to split sensitive fields into a separate table that only certain collaborators are invited into.

"Filter by current user" needs a real Collaborator field Airtable's Interface feature that auto-filters a page to whoever's logged in only works against a native Collaborator field — a field tied to an actual invited Airtable account — never against a Link to another record field pointing at a custom table like People, and not through a Lookup of a Collaborator field either. Since Hiring Manager, Approver, and Interviewer are all Links to People in this schema, true per-viewer personalization isn't available out of the box. To get it for real: add a genuine Collaborator field alongside the People link (e.g. Hiring Manager Account), invite the actual person as a base or Interface-only collaborator, and filter using "current user" against that field instead. For a demo/learning build, skip this and just use the static per-person views from Step 7.

Candidate application form

Airtable forms cannot create new linked records — a filler can only search and select something that already exists. That's a real problem here: some applicants are brand new, but some are candidates you already sourced through Outreach, and the same public form has to handle both without creating duplicate people.

Don't build the form directly on Candidates or Applications Both of those tables have Link fields a form can't safely handle — Candidates would create a duplicate person record every time someone you'd already sourced applied through it, and Applications' Candidate field has nothing to link to for a brand-new applicant. Use a dedicated intake table instead, decoupled from your real data, and let an automation decide what happens to each submission.

Optional: on the Requisition field, set Limit record selection to a view pointed at a view filtered to Status is Open (a plain Grid view on Requisitions, filter Status is Open — same mechanism as every other view in this build), so applicants can only pick reqs that are actually open. This is purely a UI restriction on the picker a human sees — it has no effect on automations, since they write to the field by record reference directly, bypassing the picker entirely.

Deliberately left out: EEO self-identification Voluntary self-ID questions (gender, race/ethnicity, veteran status, disability status) are excluded from this build on purpose. In real hiring practice, that data has to be kept separate from what a hiring manager sees — a genuinely different design than "add more fields here," requiring its own table with its own restricted permissions (see Step 8's permissions note). Add it only if you're prepared to build that separation properly, not as a shortcut on this table.

Build the form

  1. Open Application Submissions → + Add view → Form.
  2. Include: Full Name, Email, Phone, LinkedIn/Portfolio URL, Resume, Cover Letter, Requisition, Work Authorization, Requires Visa Sponsorship, Earliest Start Date, Years of Relevant Experience, How did you hear about us, Data Privacy Consent (mark Required). Leave Processed off the form entirely — it's for the automation, not the applicant.
  3. Customize the title/description, then Publish to get the shareable link (or an embed snippet, under Share form).

Automation A — brand-new applicant

  1. Trigger: When a record matches conditions — table Application Submissions. Condition: Processed is unchecked.
  2. Find records (rename "Find Existing Candidate"): table Candidates. Condition: Email is → dynamic value → trigger's Email.
  3. Condition: Find Existing Candidate → Length is 0.
  4. Create record on Candidates: Name → trigger's Full Name. Email → trigger's Email. Phone → trigger's Phone. Resume → trigger's Resume. Source → trigger's How did you hear about us.

The newer fields (LinkedIn/Portfolio, Cover Letter, Work Authorization, Visa Sponsorship, Earliest Start Date, Years of Experience) deliberately stay on Application Submissions only, not copied to Candidates — they're specific to this application, not the person in general, and Candidates should stay a record of who someone is, not what they said on one particular form. If you want any of them visible from Candidates later, add them there as Lookups through Applications rather than duplicating the data at creation time.

  1. Create record on Applications: Candidate → the record just created above → Airtable Record ID. Requisition → trigger's Requisition. Stage → Applied.
  2. Update record on Application Submissions: trigger's own record → Processed → checked.

Automation B — matches someone already sourced

Same trigger and same Find Existing Candidate step as Automation A — just the opposite branch.

  1. Condition: Find Existing Candidate → Length is greater than 0.
  2. Create record on Applications: Candidate → Find Existing Candidate result → Airtable Record ID (the person who already existed, not a new one). Requisition → trigger's Requisition. Stage → Applied.
  3. Update record on Application Submissions: Processed → checked.

No duplicate Candidates record ever gets created for this path — the submission is matched to the existing person by email instead.

Why an intake table instead of flagging duplicates afterward An earlier version of this pattern let the form write straight into Candidates and flagged duplicates for manual cleanup after the fact — workable, but avoidable. Airtable automations have no native "delete record" action, so a caught duplicate still needs a human to tidy it up. Routing every submission through Application Submissions first means the duplicate is never created at all — the Find Records/Email check happens before anything touches your real Candidates table, and Application Submissions doubles as a clean audit trail of every raw form entry.

Glossary

Linked record
A field connecting one row to a row in another table — the core mechanic that makes Airtable a database rather than a spreadsheet.
Lookup
Pulls one field's value from a linked record into the current table. Read-only, one record at a time.
Rollup
Like a lookup, but aggregates across multiple linked records (SUM, COUNT, AVERAGE).
Junction table
A table that exists only to connect two other tables many-to-many. Applications is this table in the build above.
Interface
A dashboard layer built from your views, for people who shouldn't touch the raw base directly.
Collaborator field
Airtable's native field type tied to an actual invited account — different from a Link field to a custom People table. Required for true "filter by current user" personalization in Interfaces.
Find records (automation)
An automation action that searches a table by conditions and returns a list of matches. Unlike drilling into a plain Link field, its results expose every field on the matched record — the way to reach a field on the "other side" of a link from within an automation.
Intake table
A table a public form writes to, kept separate from your real working tables (like Candidates), so an automation can decide — by matching on something like email — whether a submission is genuinely new or belongs to someone already in the system, before any real record gets created.
