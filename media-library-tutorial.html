Building a Self-Hosted Media Library

How a folder of custom-recorded covers — audio and video, organized by artist — became a searchable, publicly hosted site: a Python generator script, a static front end on GitHub Pages, and 20 GB of media served free-of-egress from Cloudflare R2.

Two Cloudflare DNS records, one Cloudflare account, two completely separate jobs: GitHub serves the lightweight app, R2 serves the heavy files.
01

Why split the site from the media

the core architectural decision

GitHub Pages is free and simple, but it isn't built for tens of gigabytes of audio and video — individual files over 100 MB get rejected outright, and Git LFS (the obvious-looking workaround) explicitly cannot be used with GitHub Pages. Pages has no mechanism to resolve an LFS pointer file back into the real binary; it just serves the 130-byte pointer text instead of your video.

The fix is to stop treating "the site" and "the media" as one thing. The site — a handful of HTML/CSS/JS files under a few hundred KB total — stays on GitHub Pages, exactly where it already was. The media moves to Cloudflare R2, object storage built for this, with zero egress fees no matter how much gets streamed.

Why R2 specifically For ~20 GB, R2's free tier covers the first 10 GB of storage; the rest runs about $0.015/GB/month — roughly 15 cents a month. Bandwidth to visitors is always free, which is the number that actually matters for a media site: every play of every song is bandwidth.
02

The generator script

build_library.py

One Python script does the actual work: point it at a folder of artist subfolders, and it writes a complete static site — no manual page-building, ever. Re-run it any time the library changes. 

# from wherever build_library.py lives
python3 build_library.py "/path/to/library" \
  --title "Zentropic Sessions" \
  --media-base-url "https://media.zentropic.co" \
  --debug

It scans recursively for recognized file types and writes six files into the library root:

  • library.html — combined view, all media
  • index.html — a redirect stub to library.html, since GitHub Pages only auto-serves a file with that exact name at a bare folder URL
  • audio.html / video.html — filtered views, same search/tile/index UI
  • styles.css, app.js, data.json — shared by all three pages

Every artist gets a Tiles view (large artwork grid) and an alphabetical text Index — both search the same underlying data, and both ignore a leading "The" when alphabetizing (The Beatles files under B, not T).

Key flags

FlagWhat it does
--titleDisplay name shown in the page header and browser tab — cosmetic only.
--media-base-urlPrefixes every track/artwork reference with this URL instead of a relative path. This is what makes the GitHub + R2 split work.
--no-artworkSkips online artwork lookups entirely — fast rebuilds while testing structure.
--debugPrints per-artist audio/video counts, artwork match sources, and any naming mismatches it finds.
03

The video naming convention

Artist_Album Name_Song

Audio files are grouped by whatever folder they physically sit in — simple, and matches how the library was already organized. Video is different: files often get dumped together rather than sorted per artist, so video artist grouping comes from the filename itself, parsed on the first two underscores: Artist_Album Name_Song.mp4.

This means a folder called Videos/ containing files named Radiohead_OK Computer_Karma Police.mov correctly splits into a "Radiohead" entry — merged with the existing Radiohead audio folder if the names match — rather than everything lumping under one artist named "Videos".

Parsed videos get their song title shown instead of the raw filename, and tracks are grouped under an album section heading in the track list — a real Artist → Album → Song catalog, not a flat file dump.

04

Controlling artwork manually

for the artists the internet gets wrong

Artwork resolves in priority order: an overrides file, a local cover image, then an online lookup (Deezer, then iTunes), then a generated monogram tile as a last resort.

Option A — drop a file in the folder

Name it exactly artist.jpg (or .png/.webp, or cover.*) and place it directly inside that artist's own folder. Same filename every time — the folder is what identifies the artist, not the image name. Square, 500–800px per side is the sweet spot for a tile shown at 112×112 on a retina screen without bloating page weight.

Option B — artwork-overrides.json

For artists that don't map to one folder — like video-only artists identified purely by filename — a JSON file at the library root maps artist name to either a local path or a full URL: 

{
  "The Beatles": "The Beatles/artist.jpg",
  "Fleetwood Mac": "https://example.com/some-photo.jpg"
}
Real bug, caught in testing An early version of the artwork lookup silently hit iTunes far faster than Apple's documented ~20 requests/minute limit, which doesn't error — it just quietly returns empty results. That looked identical to "no artwork exists" for whichever well-known artists happened to get scanned after the limit kicked in. The fix was a real rate limiter, not a workaround.
05

Connect your domain to GitHub Pages

so the site itself has a home

Do this before touching R2 — it's the piece that actually needs to exist first. Three parts:

  1. Verify domain ownership with GitHub — profile/org Settings → Pages → Custom domain verification. GitHub gives you a TXT record; add it in Cloudflare's DNS tab (Type: TXT, paste the name and value exactly, case-sensitive).
  2. Add the domain in your repo — repo Settings → Pages → Custom domain → enter the domain → Save.
  3. Set the real DNS records in Cloudflare — four A records for the apex domain, one CNAME for www: 
# apex (zentropic.co) — four A records:
185.199.108.153
185.199.109.153
185.199.110.153
185.199.111.153

# www.zentropic.co — one CNAME:
yourusername.github.io
Cloudflare-specific gotcha Set these to DNS only (gray cloud, not the orange "proxied" one) while GitHub issues its HTTPS certificate. Proxying too early can interfere with Let's Encrypt validation. Once HTTPS is confirmed working, "Enforce HTTPS" becomes available in repo Settings → Pages.
06

Set up the Cloudflare R2 bucket

object storage for the heavy files
  1. Cloudflare dashboard → R2 → Create bucket. Lowercase, hyphens only — ours is medialibrary.
  2. Open the bucket → Settings → Public Access → Custom Domains → Connect Domain → enter a subdomain (media.zentropic.co) that isn't already used by the main site.
  3. Cloudflare auto-creates the DNS record for this one — no manual record needed, unlike the GitHub TXT record.
Skip the *.r2.dev URL Cloudflare's own docs call the quick *.r2.dev subdomain rate-limited and meant for testing, not production. A real custom domain avoids that ceiling entirely.
07

Create an API token

R2 → Overview — not inside the bucket

This one moves around in Cloudflare's UI, so the reliable path: R2 → Overview page → "Account Details" section → Manage next to API Tokens.

  1. Create Account API token.
  2. Permission: Object Read & Write.
  3. Scope it to the medialibrary bucket specifically — not "all buckets."
  4. Copy the Access Key ID and Secret Access Key immediately — the secret is shown exactly once.
  5. Grab the Account ID from the same page for the endpoint URL.
Account ID ≠ Member ID Cloudflare shows more than one long hex string in its UI. Using the wrong one produces a connection that hangs indefinitely with no error — not a fast failure, a silent stall. If rclone lsd never returns and never errors, this is the first thing to check.
08

Upload with rclone

20 GB is not a dashboard drag-and-drop job
# ~/.config/rclone/rclone.conf
[r2]
type = s3
provider = Cloudflare
access_key_id = <your access key>
secret_access_key = <your secret key>
endpoint = https://<your account id>.r2.cloudflarestorage.com
acl = private
no_check_bucket = true

no_check_bucket = true matters whenever the token is scoped to one bucket rather than the whole account — without it, rclone's default existence check fails with a permissions error before it even tries to upload anything. 

# confirm the connection first
rclone lsd r2:medialibrary

# then the actual upload — preserves Artist/song.ext structure as-is
rclone copy "/path/to/library" r2:medialibrary --progress

copy, not sync — it adds and updates files without deleting anything from the bucket if the local folder and the bucket ever diverge. If the transfer gets interrupted, re-running the exact same command resumes rather than starting over.

A false alarm worth knowing about Testing the R2 endpoint with macOS's built-in curl can throw an SSL handshake error that looks alarming — that's a known incompatibility between old system LibreSSL and modern TLS negotiation, not a real problem with R2 or your credentials. rclone uses its own TLS stack and isn't affected.
09

Wire it together and go live

the last mile
  1. Regenerate with --media-base-url pointed at the R2 custom domain, so every track and locally-hosted artwork reference resolves against it instead of a relative path. Anything already an absolute URL — an online artwork match, or an override pointing at an external photo — is left untouched.
  2. Move the generated files — library.html index.html audio.html video.html styles.css app.js data.json — into the GitHub Pages repo. Everything else (artist folders, audio, video, cover images) stays in R2.
  3. If the whole thing lives in a subfolder of the repo (e.g. medialibrary/), nothing in the files themselves needs to change — every internal reference is relative to itself, and the media links are already absolute URLs. Only the visiting URL changes, to zentropic.co/medialibrary/.
  4. Confirm in a browser's Network tab that a real media request actually resolves to media.zentropic.co with a 200 — not just that the page loads.
10

library.html, and downloading tracks

two late additions

The combined page is named library.html, not index.html — a deliberate rename. Since GitHub Pages only auto-serves a file named exactly index.html at a bare folder URL, the generator now also writes a tiny index.html redirect stub alongside it, so visiting the bare folder still lands on the real page instead of 404ing.

Each track row also has a ↓ download button. It works by fetching the file and forcing a save dialog via a blob download, rather than just linking to it — a plain link's download attribute is unreliable once the file lives on a different domain than the site itself, which is exactly the split this whole setup created.

Requires one R2 setting Cross-origin fetches are blocked by the browser unless the R2 bucket explicitly allows them. Bucket → Settings → CORS Policy → Edit CORS policy: 
[
  {
    "AllowedOrigins": ["https://zentropic.co", "https://www.zentropic.co"],
    "AllowedMethods": ["GET"],
    "AllowedHeaders": ["*"]
  }
]

Without this, the download button degrades gracefully — it opens the file in a new tab instead of forcing a save dialog, which still works, just requires an extra right-click → Save As.

11

What the site actually does

for reference
  • Search matches artist name, song title, and album — not just the artist.
  • Tiles / Index toggle — visual grid or a text-only alphabetical list, same data either way, "The" ignored when alphabetizing.
  • All / Audio / Video nav — three pages, one shared dataset, filtered client-side.
  • Session queue — a "+" per track and a "Queue all" per artist build a play-through queue with a persistent bottom player bar, Previous/Next, and auto-advance. Resets on tab close by design — nothing persists, nothing is shared between visitors.
  • Download — a ↓ per track, forced save dialog once R2's CORS policy allows it.
