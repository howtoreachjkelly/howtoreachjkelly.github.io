Before you start

One mental model to hold onto for the entire build.

Coming from spreadsheets, the instinct is one giant tab with a column for everything. Airtable's actual advantage only shows up once you split that into separate tables for separate things — a candidate, a job requisition, an interview — and connect them with Link to another record fields instead of retyping text.

Everything in this guide — lookups, rollups, automations — is built on top of that one idea. Get the linked-record structure right first; everything else is decoration on top of it.

Setup Create a new base from scratch (not a template) at airtable.com → Add a base → Start from scratch. Name it Hiring Workflow. You'll add 8 tables to it over the next 8 steps.
01

Departments & People

The foundation tables — everything else in the base links back to these, so get them right first.

Table: Departments

  1. Click + Add or import at the bottom of the table bar → Create blank table. Rename it Departments.
  2. Rename the default Name field (it's your Primary field — every table needs exactly one, it's what shows up when this table is referenced elsewhere).
  3. Add field VP Owner — type Link to another record → target table People (create People first if it doesn't exist yet, or leave this field for later and come back to it).
  4. Add field Budget Headcount — type Number, integer format.

You'll add an Open Reqs rollup field here later, once the Requisitions table exists — rollups can only reference tables that already exist.

Table: People

Every recruiter, hiring manager, interviewer, and approver in the org goes here — this is the table that makes the approval chain in Step 5 possible.

Leave Applications, Approvals, and Candidate Count for later — Airtable auto-creates the reverse link once you build the Applications and Approvals tables and link back to Requisitions from there.

Why status is a single select, not text A Single Select field is what an automation can watch for changes on ("when Status becomes Pending Approval, do X"). A plain text field can't trigger anything — this distinction matters everywhere in this build.

Table: Applications — the junction table

A candidate can apply to multiple reqs. A req gets multiple candidates. That's a many-to-many relationship, and Airtable has no direct way to link two tables many-to-many — you always need a third table sitting in between, with a single link to each side. That's what Applications is.

FieldTypeNotes
Application IDFormulaPrimary field — see below
CandidateLink to recordLinks to Candidates, single record only
RequisitionLink to recordLinks to Requisitions, single record only
StageSingle selectApplied / Phone Screen / Onsite / Offer / Hired / Rejected
RecruiterLink to recordLinks to People
{Candidate} & " → " & {Requisition}
The pattern to remember Any time you hit "this could link to more than one of that, and that could link to more than one of this" — stop, and build a junction table instead of trying to force a direct link. You'll see it again with Interviews and Approvals.

Back on the Applications table — add two rollups now

With Interviews built, go back to Applications and add:

FieldTypeConfig
Avg Interview ScoreRollupThrough the Interviews link → AVERAGE(values)

A Lookup pulls one linked record's field over as-is. A Rollup aggregates across multiple linked records with a function like SUM, AVERAGE, or COUNT. Use Lookup for "what's this candidate's name," Rollup for "what's the average score across all their interviews."

05

The approval chain

⬤ hardest step in this build

A checkbox that says "manager approved" is a single gate, not a chain. A real chain means multiple approvers acting in sequence, where step 2 can't act until step 1 clears. Do everything else in this guide first — come back here once the rest of the base is stable.

Table: Approvals — a generic, reusable approval engine

One table handles req sign-off and offer sign-off — you don't need two separate systems.

FieldTypeNotes
Approval IDFormulaPrimary field
TypeSingle selectReq Approval / Offer Approval
Related ReqLink to recordBlank for offer approvals
Related OfferLink to recordBlank for req approvals
ApproverLink to recordLinks to People
Approval OrderNumber1, 2, 3 — this is what makes it a sequence
StatusSingle selectPending / Approved / Rejected
CommentsLong text

Wiring the chain — five steps

  1. Requisition's Status changes to Pending Approval. An automation (built in Step 6) creates several linked Approval records at once — e.g. Order 1 = Dept VP, Order 2 = Finance, Order 3 = CHRO — branching on the req's Priority or Salary Band.
  2. Every Approval record starts as Pending.
  3. Build a view filtered to Approver = me AND Status = Pending — but add one more condition: a formula field that checks whether every lower Approval Order on the same req is already Approved. That formula is the actual gate — it's what keeps approver #2 from seeing the request before approver #1 has acted.
  4. When the last approver in the chain sets Status to Approved, an automation flips the parent Requisition to Approved.
  5. If any approver Rejects, an automation flips the Requisition back to Draft and notifies the Hiring Manager.
Where people get stuck The gate in step 3 is a formula field, not a filter you can build with dropdowns alone. If you're new to Airtable formulas, this is worth a dedicated session rather than trying to knock it out alongside everything else.

08

Interfaces & permissions

The last mile — handing this to people who should never see the raw base.

Airtable's Interfaces layer builds a dashboard on top of your views — this is how you hand the base to an exec without teaching them what a grid view is. Build views first (Step 7), then build Interfaces from them; if you rebuild the underlying view later, the Interface needs rework, so don't build Interfaces until the views are stable.

Field-level and record-level permissions (an interviewer edits their own score but can't see salary bands) require Airtable's Enterprise plan admin panel — Team and free plans only permit locking at the table level. On lower plans, the workaround is to split sensitive fields into a separate table that only certain collaborators are invited into.

Glossary

Linked record
A field connecting one row to a row in another table — the core mechanic that makes Airtable a database rather than a spreadsheet.
Lookup
Pulls one field's value from a linked record into the current table. Read-only, one record at a time.
Rollup
Like a lookup, but aggregates across multiple linked records (SUM, COUNT, AVERAGE).
Junction table
A table that exists only to connect two other tables many-to-many. Applications is this table in the build above.
Interface
A dashboard layer built from your views, for people who shouldn't touch the raw base directly.
